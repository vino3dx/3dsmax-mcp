## 3. 本轮新发现的事实性缺陷（已在实机复现）

### 3.1 `scene_statistics` 分类全为 0（数据失真，最严重）

实测返回：

```json
{"objects":65,"geometry":0,"shapes":0,"lights":0,"cameras":0,"helpers":0,
 "spacewarps":0,"systems":0,"other":65,"totalFaces":18786,"totalVerts":11618}
```

原因：`(superclassof o) as string` 在本机返回的是 `GeometryClass` / `shape` / `light` / `camera` / `helper`（大小写与拼写都不统一），而 `mcp_scene.ms:76-83` 比较的是 `"Geometry"` / `"Shape"` / `"Light"` / …，只有 `other` 分支能命中。

影响：任何依赖分类统计的 AI 判断都会得到"场景里 65 个对象全是 Other"。这是"返回 ok 但数据不真实"的典型案例。

### 3.2 `doctor.py` 永远报 "broken autoloader"（诊断说谎）

`doctor.py:164` 用 `line.startswith("local bridgeFile = @\"")` 解析路径，而 `install.py:196` 生成的是 `mcpLoaderBridgeFile = @"..."`（全局变量，没有 `local`）。实测：

```
[FAIL] 3ds Max 2022 [ENU]: broken autoloader
       could not parse the bridge path out of ...\startup\3dsmax-mcp-bridge.ms
```

而该 loader 指向的 `...\scripts\3dsmax-mcp\mcp_bridge.ms` 存在、桥接正在 8765 正常服务。安装器/维护面板若直接复用这段诊断，会把正常环境报成故障。

### 3.3 `polyop.getNumMapChannels` 不存在

探测返回 `Unknown property: "getNumMapChannels"`，真实接口是 `polyop.getNumMaps`。任何"UV 通道数"采集必须先探测再调用，否则异常文本会把整个 `polyop` 结构体（约 6 KB）吐进响应 —— 这也说明**错误信息必须截断**。

### 3.4 `execute_python` 的多行代码在本次审计中被误判为缺陷（澄清，非项目 bug）

排查过程中出现 `try:/n` 的语法错误，最终定位为**我方测试 heredoc 的转义被改写**（`\n` → `/n`），用文件方式重测后 `execute_python` 恢复正常（能拿到 `py 3.7.12`、65 个对象、Standard 材质 55 个属性）。记录在此以免下一轮重复踩坑：**不要在 heredoc 里写反斜杠转义，改用 Write 落文件再执行。**

## 4. 事件机制实测矩阵（Phase B 的设计依据）

这一节全部是实测结论，不是文档推断。

### 4.1 `callbacks.addScript` —— 可用，且**同步**触发

语法必须是 `callbacks.addScript <name> "<code>"`；`id:` 只接受 **Name**（传整数报 `Callback script ID must be a name`）。

**接受（20 个）**：
`#selectionSetChanged`、`#nodeRenamed`、`#preRender`、`#postRender`、`#preRenderFrame`、`#postRenderFrame`、`#preImport`、`#postImport`、`#preExport`、`#postExport`、`#sceneUndo`、`#sceneRedo`、`#filePreOpen`、`#filePostOpen`、`#filePreSave`、`#filePostSave`、`#modPanelObjPostChange`、`#unitsChange`、`#layerCreated`、`#layerDeleted`

**拒绝（35 个，本机不支持）**：
`#nodeAdded`、`#nodeDeleted`、`#preSave`/`#postSave`、`#preOpen`/`#postOpen`、`#preNew`/`#postNew`、`#preReset`/`#postReset`、`#preMerge`/`#postMerge`、`#preUndo`/`#postUndo`、`#preRedo`/`#postRedo`、`#preHold`/`#postHold`、`#preFetch`/`#postFetch`、`#preRelease`/`#postRelease`、`#systemStartup`/`#systemShutdown`、`#prePluginLoad`/`#postPluginLoad`、`#timeUnitChange`、`#layerChanged`、`#preImportFile`/`#postImportFile`、`#preExportFile`/`#postExportFile`

实测行为：脚本执行 `select b` 后 `#selectionSetChanged` **立即**收到 3 次；`b.name = ...` 后 `#nodeRenamed` 立即收到。
→ 这类回调是**同步**的，意味着"handler 只准置脏标记，不准扫描"，否则每次选择都会拖慢编辑器。

### 4.2 `NodeEventCallback` —— 可用，签名是 `(Name, Array)`

用 0/1/2/3 参数各注册一个 handler，只有 2 参数的被调用，实参类型为 `Name`（事件名）+ `Array`（节点数组）。MAXScript 参数个数是**严格**的，多一个少一个都会抛 `Argument count error` 且**异常只进 Listener，桥接看不到** —— 这就是"注册成功但毫无反应"的隐蔽失败模式。

实测触发情况：

| 事件 | 脚本改动是否触发 | 备注 |
| --- | --- | --- |
| `added` | ✅ 触发（异步，随泵派发） | |
| `deleted` | ✅ 触发 | |
| `selectionChanged` | ❌ 未触发 | 改用 `#selectionSetChanged` |
| `nameChanged` | ❌ 未触发 | 改用 `#nodeRenamed` |
| `geometryChanged` | ❌ 未触发 | 顶点编辑、convertToPoly 均无事件 |
| `topologyChanged` | ❌ 未触发 | |
| `materialStructured` | ❌ 未触发 | 赋材质无事件 |

结论：**不能假设 NodeEventCallback 是全能事件源**。它只可靠提供 added / deleted；其余一律退回 `callbacks.addScript` 的同步通知，仍拿不到的（几何内容变化、材质赋值）走"按需指纹校验 + 工具写入时主动置脏"。

### 4.3 无法事件化的部分（必须按需或轮询）

- 新建/重置/合并场景（无 `#preNew`/`#postNew`/`#preMerge`）→ 用场景身份（文件路径 + 对象句柄集合）在 tick 里做廉价比对；
- 几何/拓扑内容变化、材质赋值 → 指纹或脏标记；
- 渲染进度（百分比、已用时间）→ 无回调，只能 `#preRender`/`#postRender` 夹出"起止"，中间态用受控轮询或 `renderers.current` 的进度接口（Phase D 验证）；
- 图层重命名/属性变化（`#layerChanged` 不存在）→ `NodeEventCallback layerChanged` 待验证，否则按需快照。

## 8. 风险与设计约束

1. **单线程**：所有场景访问都在 Max 主线程，靠 25 ms WinForms 泵驱动。上下文维护**必须**挂在 `mcpOnTick` 之后，不允许新建第二个定时器（会与泵竞争并放大重入风险）。
2. **`mcpPumpBusy` 不可动**：上一轮的栈溢出根因是派发期间重入，任何新增的 tick 逻辑都要在闸**之外**且必须极廉价。
3. **回调同步性**：`#selectionSetChanged` 是同步的 → handler 里只准 `mcpCtxMarkDirty #selection`，禁止扫描。一次全量 `mcpNodeInfo` 是 7 ms，乘以每次选择就会毁掉交互手感。
4. **序列化成本 > 采集成本**（1.4 节实测）→ 上下文接口默认返回摘要（KB 级），明细走分页参数；不允许"一次返回 2000 个对象的完整信息"。
5. **MAXScript 语法雷区**（本轮再次确认）：参数个数严格；`where` 是保留字；`for x in <函数名>` 报 "No map function"；顶层不能 `local`；匿名 `fn` 不能捕获外层局部变量。
6. **错误文本可能极大**（`polyop` 结构体 6 KB）→ 所有新 handler 的异常消息统一截断（如 400 字符）。
7. **文档是门禁**：`scripts/verify.py` 会校验 README 工具总数/分类表/档位表、`docs/tools.txt`、`examples/maxscript/listener_cheatsheet.ms`。新增工具必须同步这些文件，否则 verify 直接红。
8. **未提交改动**：工作区已有 18 改 1 增，Phase B 起每阶段单独提交，不 amend、不覆盖。

## 9. 开发路线（Phase B → F）

### Phase B — 内置客户端 + 数据监听基础设施

新增文件（不改既有逻辑，只在 `mcp_bridge.ms` 的模块列表尾部追加）：

| 文件 | 职责 |
| --- | --- |
| `src/ms/mcp_events.ms` | 回调注册/注销（幂等）、事件环形缓冲（最近 N 条）、`mcpCtxRevision` 计数器、按域置脏 |
| `src/ms/mcp_context.ms` | 分域缓存 + 采集器 + `context_*` 处理器 + `mcpCtxTick()` |
| `src/ms/mcp_ui.ms` | `Vino 3dsMax MCP` 面板（rollout + dotNet 控件，先不做 WPF） |
| `src/python/maxmcp/context.py` | Python 侧快照缓存、diff 合并、失效策略 |
| `src/python/maxmcp/catalog/context.py` | 新 category `context` 的工具声明 |

关键设计：

- **一个版本号**：`mcpCtxRevision`（整数），任何事件/写入工具都 `+= 1`；每域带 `revision` + `updatedAt` + `source` + `valid`。
- **三档更新**：事件置脏（O(1)）→ tick 内按需重算脏域（廉价域直接算，昂贵域标 stale）→ `context_get` 显式 `refresh:true` 才全量。
- **幂等注册**：`mcpEventsStart()` 先 `mcpEventsStop()`，再逐个 `try` 注册；记录 `{name, ok, error}` 到能力表，供面板和 `bridge_status` 展示。
- **回调只置脏**，不扫描；tick 每 8 次（≈200 ms）检查一次"是否有脏域"，无脏直接返回。
- **场景身份比对**（应对无通知的新建/重置/合并）：文件路径 + 对象数 + 首尾句柄，7 ms 级别，且只在脏或每 N 秒做一次。

验收：`bridge.log` 无 `module failed`；面板能开；`context_get` 返回 revision/sections/timestamps；连续 200 次选择操作后 Max 无卡顿、revision 单调递增。

### Phase C — 场景感知（Scene / Objects / Selection / Geometry / Materials / Textures / Modifiers）

- 修 3.1（superclass 分类）并加回归断言；
- `mcpNodeInfo` 拆成 `brief` / `full` 两档，`get_selection` 用 brief，新工具用 full；
- 材质解析改为"类驱动"：先用 `getPropNames` 枚举，再按类映射常用别名，输出 `properties: {name: value}` + `mapSlots: [{slot, channel, mapClass, filename}]`，未知字段如实留空并标注 `unsupported`；
- 贴图采集加尺寸、重复引用（同文件多图节点）、未使用（不可从 sceneMaterials 到达）；
- UV 通道用 `polyop.getNumMaps` + `polyop.getMapSupport`，Mesh 用 `meshop`，两者都失败时明确报 `geometryType` 不支持。

### Phase D — 动画 / 骨骼 / 灯光 / 相机 / 渲染

- `rig_summary`：按 `BoneGeometry` / `Biped_Object` / `CATBone` / 虚拟体 分类统计，Skin 数量与权重覆盖度；**每类都要给出"检测到几个、依据是什么、失败原因"**；
- `animation_summary`：控制器类型分布、关键帧总数、约束清单、Morph 清单；
- 灯光/相机补锥角、衰减、区域尺寸、阴影类型、目标、正交、景深、曝光；
- `render_state`：`#preRender`/`#postRender` 记录起止与耗时，进行中返回 `rendering:true` + 已用时间（无进度 API 时明确写 `progressUnavailable`）；
- 渲染元素明细（名称/类型/启用/输出路径）。

### Phase E — 资源与工程管理

- `project_info`（工程目录、路径配置、XRef、缺失资源、目录结构）；
- `asset_report`（尺寸/重复/未使用/缺失/外部依赖，分页）；
- `scene_health`（重名、零面、空组、未使用材质、丢失贴图、孤立骨骼）；
- `scene_cleanup`（只做"报告 + 显式确认后执行"，默认 dryRun）；
- 安装器/维护面板接 `install.py` / `doctor.py`（顺带修 3.2）。

### Phase F — 实机验证

- 扩展 `scripts/verify.py`（静态）+ 新增 `scripts/test_context.py`（实机：事件→revision→context_get 一致性）；
- 200 次选择/50 次建模/10 次存盘的稳定性循环；
- 断线/重启桥接/重启 Server 的恢复测试；
- 回归跑通既有 `verify.py` + `test_e2e.py`，确认 384 工具一个不退。

## 11. 需要你确认的三个决策

1. **面板技术选型**：建议 **MAXScript rollout + dotNet 控件**（与桥接现有依赖一致，2020+ 通用），不做 WPF、不做 C++。是否同意？
2. **Context 出口形态**：建议 **工具为主**（`context_get` / `context_refresh` / `context_stats`），同时把 `resources/list` 填成 `max://scene/context` 只读资源（部分客户端支持订阅）。是否要资源，还是只做工具？
3. **工具增量规模**：建议本轮 **只加 12–16 个 context/诊断类工具**，其余靠加深既有工具；不新增 50 个"看起来完整"的薄工具。是否同意这个尺度？
